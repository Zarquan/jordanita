    >   # Calycopis — IVOA Execution Broker Prototype: Project Summary
    >   
    >   ## What it is
    >   
    >   Calycopis (named after a genus of butterflies) is a **prototype implementation of the IVOA Execution Broker service** — an abstract API that lets clients submit an *execution request* (what to run + required resources) and receive *offers* for execution sessions, then accept an offer and have the broker prepare, execute, and monitor the task through a common interface. The design goal is one API over heterogeneous platforms (OpenStack, Docker, Kubernetes, Slurm, Panda, etc.). Early work began as "CIRASA-planner" (INAF); current development is part of the **SKA SRCNet program**. Licensed GPL-3.0, maintained under `uksrc/Calycopis-broker` (with a `Zarquan` fork as `origin` and an old fork kept in `attic/`).
    >   
    >   ## Current status
    >   
    >   - **Version 1.0.7-SNAPSHOT** (`config.yaml` drives all versions via `bin/versions.sh`): schema `1.0.7`, Spring OpenAPI `1.0.7-SNAPSHOT`, Python client `1.0.7.dev5`.
    >   - **349 main-source Java files** — 304 in `engine/`, 42 in `spring/` — Spring Boot 4.1.0 parent, **Java 21**.
    >   - Depends on generated schema classes (`net.ivoa.calycopis:calycopis-openapi-spring`) pulled from the UKSRC Nexus; PostgreSQL (H2 unsupported — relies on `GENERATE_SERIES`); `docker-java` for container control; Spring Security + OAuth2 resource server.
    >   - Recent commits (Aug 2026) show active work: TRD-129/TRD-125 merges, Docker buildpack image, resource-increase and utility-container preloading, test timeouts/fixes.
    >   
    >   ## Architecture
    >   
    >   The defining design decision is a **strict two-tree split**:
    >   
    >   - **`engine/`** — framework-neutral domain logic (interfaces, JPA entities via `jakarta.persistence.*`, factories, validators, processing). **Zero Spring imports**; the intent is that this layer could be ported to a different DI/web framework.
    >   - **`spring/`** — all Spring wiring: web delegates, `@Repository` interfaces (centralised in `spring/jpa/`), `@Component` platform impls, `@Scheduled` processing loop, security.
    >   
    >   Every domain concept follows a **three-tier Entity/Factory/Validator/Repository pattern**: abstract base (`engine/entities/<concept>/`) → schema type (`.../simple/`) → platform implementation (`.../simple/<platform>/`), with validators using exact class matching (`getClass() ==`) in a chain-of-responsibility `ValidatorFactory`. The two platforms are **mock** and **docker**, selected by Spring profile (`@Profile("mock")` / `@Profile("docker")`); each platform impl registers its own validators/factories at startup.
    >   
    >   ## API surface (current)
    >   
    >   Server runs on port **8082**; models are now `Ivoa*`-prefixed (e.g. `IvoaExecutionRequest`, `IvoaOfferSetResponse`, `IvoaAbstractExecutionSession`). Delegates implement the generated `*ApiDelegate` interfaces:
    >   
    >   | Delegate | Method | Endpoint |
    >   |---|---|---|
    >   | `OffersetsApiDelegateImpl` | `offerSetSelect(uuid)` | `GET /offersets/{uuid}` |
    >   | `SessionsApiDelegateImpl` | `sessionSelect(uuid)` / `sessionUpdate(...)` | `GET` / `POST /sessions/{uuid}` |
    >   | `RequestsApiDelegateImpl` | `executionRequest(...)` | `POST /requests` |
    >   | `DirectApiDelegateImpl` | `directExecution(...)` | `POST /direct` (direct execution path) |
    >   | `AdminIdentityController` | `createIdentity(...)` | `POST /admin/identities` (local, not in schema) |
    >   
    >   Content negotiation covers JSON/YAML/XML via `YamlConverter`; actuator exposes health/info/metrics.
    >   
    >   ## Security & identity (newer than AGENTS.md)
    >   
    >   - `spring/security/`: `SecurityConfig` — **GET is public, POST requires auth** (HTTP Basic or Bearer JWT via `spring-security-oauth2-resource-server`); `/admin/**` requires the `ADMIN` authority; stateless sessions; BCrypt passwords.
    >   - **Identity model** in `engine/entities/identity/` — local accounts (username + password) and OIDC identities (issuer + subject). `AdminAuthenticationProvider` / `LocalAuthenticationProvider` handle auth; `IdentityResolver` links the authenticated principal to `IdentityEntity` so sessions are attributed per user. The Python test suite seeds users through the admin endpoint.
    >   
    >   ## Processing lifecycle
    >   
    >   - `ProcessingServiceImpl` (engine) + `SpringProcessingServiceImpl` (`@Scheduled(fixedDelay = 1000)`) drive a queue of `ProcessingRequestEntity`s through `preProcess`/`postProcess` with a `ProcessingTransactionHandler`.
    >   - Per-component actions (`Prepare/Monitor/Release/Cancel/Fail` request entities) and per-session actions (`PrepareSession/ReleaseSession/CancelSession/UpdateSession`), plus an `AbstractResourceOffer`/`SimpleComputeResourceOffer` booking/query framework (`engine/query`, `spring/query`).
    >   - Mock entities simulate work with configurable delays/loop counts (`mock-entities.actions` in `application.yaml`); the docker platform runs real containers via the Podman socket.
    >   
    >   ## Costs & metrics
    >   
    >   `engine/entities/cost/` and `engine/entities/metric/` (`AbstractCostItem`, `SimpleMinMaxFloatCost`, `MetricItemBean`, …) provide min/max ranges advertised per session/compute — monetary, energy, and carbon costs plus compute/IO benchmarks, configured in `application.yaml`. A `demo/` deploys **three brokers with different cost profiles** (alpha = green HPC, beta = cloud, gamma = budget) to show offer comparison.
    >   
    >   ## Testing
    >   
    >   - **Python pytest suite** (`tests/python/`, ~116 tests): split into `mock/` (validators, direct execution, stress), `docker/` (real container runs: bind mounts, volume mounts, androcles md5, stress), and platform-agnostic `any/` (resource registration, costs & metrics, identity auth). Uses the generated Python client; `conftest.py` seeds identities and creates authenticated clients.
    >   - **curl examples** in `tests/curl/` are acknowledged as largely outdated reference material.
    >   - Java tests are minimal (a skaha client placeholder `.txt`).
    >   - CI: `.github/workflows/build-packages.yml` builds/publishes broker packages and a container image (Paketo buildpacks).
    >   
    >   ## Infrastructure & conventions
    >   
    >   - `docker/`: `developer-tools` (Fedora dev container), `fedora-base`, `java-runtime`, `python-tester`, `docker/compose/calycopis-compose.yml` (broker + postgres + client), and build/clean/push scripts. Credentials live outside the repo in `/etc/calycopis/{database,admin,spring}.yaml`.
    >   - Notable quirk (documented in AGENTS.md): the broker talks to **host Podman via a bind-mounted socket**, so bind-mount paths resolve against the *host* filesystem — files created inside the dev container are not visible to application containers, and tests must compute reference checksums in-container rather than via local file I/O.
    >   - House rules: no binary files in the tree, no suppressed errors, GPL licence headers + `AIMetrics` blocks on modified files, no ternary operators, and a ban on fragile DI patterns (`@Transient` helpers, static singletons, `ApplicationContextAware`).
    >   
    >   ## Areas worth flagging
    >   
    >   1. **AGENTS.md lags the code** (describes 1.0.3, `OfferSetRequest`/`OfferSetResponse` naming, no security) — the doc should be refreshed to match the current `Ivoa*` models, identity/security layer, costs-and-metrics, and the `/requests` + `/direct` endpoints.
    >   2. `engine/entities/data/` has grown platform/backend-specific subtrees (amazon, ivoa, docker `file`/`http`/`link`/`stop`, mock) that go beyond the schema's abstract kinds — worth confirming which are experimental.
    >   3. Recent history includes several "Skipping broken tests" commits, so the passing-test count understates coverage.
    >   
    >   Overall: a well-structured, actively developed broker prototype whose clean engine/spring separation and consistent three-tier entity pattern make it genuinely portable, with real container execution, authentication, and a meaningful cross-language test suite.

    >   
    >   **The trailing slash on the source is important.** `/root/.dsh/` means "the *contents* of this directory" — it syncs into the existing `temp/.dsh` and keeps that directory name. Without it (`rsync -a /root/.dsh dest/`), rsync would nest a second `.dsh` directory inside the destination.
    >

    >   
    >   ## Optional variations
    >
