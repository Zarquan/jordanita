    >   I've traced the full mechanism through the harness source. Here's the honest picture and the practical options.
    >   
    >   ## How the sandbox works
    >   
    >   The file-effect sandbox is a **closed three-mode vocabulary** — there is **no per-directory allowlist** option:
    >   
    >   | Mode | File writes allowed |
    >   |---|---|
    >   | `read-only` | none |
    >   | `workspace-write` (current default) | workspace root only (+ platform temp) |
    >   | `danger-full-access` | everywhere (no confinement) |
    >   
    >   The `dsh-sandbox-policy` docs are explicit: *"One primary workspace root per session — extra writable roots are **not part of** `SandboxExecutionPolicy`."* So a config like `allowedPaths: [/root/.m2]` doesn't exist today — I checked the provider config (`dsh-sandbox-local`/`dsh-sandbox-policy` only expose `mode` + `workspaceRoot`/runner options). Reads are never confined, which is why `/etc/calycopis` was never a problem — only *writes* to `/root/.m2` triggered the prompts.
    >   
    >   ## The supported ways to stop the prompts
    >   
    >   **1. Set `DSH_PERMISSION_MODE=danger-full-access` on the harness process (the intended switch).**
    >   The shipped base patch resolves the default as:
    >   ```yaml
    >   mode: !!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'
    >   approval.policy: !!js (process.env.DSH_PERMISSION_MODE ?? 'workspace-write') === 'danger-full-access' ? 'never' : 'ask'
    >   ```
    >   So one env var both disables confinement **and** flips the approval policy to `never` — no more prompts for anything, including Maven's `.m2` writes. It must be present when the harness boots (config is resolved at load), so it goes in the `broker-dev` container's launch environment (podman run / compose `environment:` / service unit), then restart the harness. Downside: it's global — it removes confinement for *all* paths, not just the specific ones.
    >   
    >   **2. Keep `workspace-write` and route the outside-writes into the workspace (best if you want to keep confinement).**
    >   Since writes are confined to the workspace root, point the tools at workspace paths instead:
    >   - Maven: `-Dmaven.repo.local=<workspace>/build/m2` (seed it once with `cp -a /root/.m2 build/m2` so nothing re-downloads — this is the one I couldn't do because `.m2` is 1.2 GB)
    >   - Python: venvs under `build/` (as I did with `build/test-venv`)
    >   - `/etc/calycopis` needs no change — reads are always allowed
    >   
    >   This is the "narrowest trust" approach: no prompts, sandbox still on, but the first Maven run needs the one-time seed copy.
    >   
    >   **3. Just answer the prompts (current behaviour).** Each approved escalation is a one-shot grant for that exact command — it does *not* persist for the session. This is the designed gate for occasional needs; it's just noisy when a tool writes `.m2` on every build.
    >   
    >   **4. (Advanced) Patch the profile** — `$DSH_HOME/profiles/web/cordis.patch.yml` is currently `[]`; you could pin `sandbox-policy.config.mode: danger-full-access` there. But since the vocabulary is closed and extra roots aren't supported, the only meaningful override is the same `danger-full-access` as option 1 — so the env var is simpler.
    >   
    >   ## Recommendation
    >   
    >   - If you're comfortable with an unconfined dev container: **option 1** — set `DSH_PERMISSION_MODE=danger-full-access` in the `broker-dev` container launch and restart the harness. Cleanest, and it also removes future prompt friction for other tools.
    >   - If you want to keep file-effect confinement: **option 2** — a one-time `cp -a /root/.m2 build/m2` plus `-Dmaven.repo.local` (and I'd also recommend adding `build/m2` to `.gitignore`).
    >   
    >   One caveat: this sandbox governs file effects only — network is already unrestricted in every mode, so nothing about connectivity changes either way.
    >   
    >   If you tell me how the `broker-dev` container is launched (the run command/compose file), I can add the `DSH_PERMISSION_MODE` env var to it for you.
