    >   Your environment variable is

    >   ```bash

    >   However Docker clients normally expect
    >   
    >   ```bash
    >   DOCKER_HOST=unix:///run/user/1000/podman/podman.sock
    >   ```
    >   
    >   Notice the required `unix://` prefix.
    >   
    >   Likewise, the Maven plugin's `docker.host` property expects the Docker host URI, not just the socket filename.
    >   
    >   So try
    >   
    >   ```bash
    >   export CONTAINER_HOST=unix:///run/user/1000/podman/podman.sock
    >   ```

    >   This result strongly confirms a **Unix-socket permission/UID-mapping problem**, not an image export problem.
    >   
    >   Your development image apparently runs as container root by default, while `curlimages/curl` deliberately runs as an unprivileged user. With rootless Podman, the host user who owns the socket is mapped to UID `0` inside the container user namespace. Podman documents that the calling host user maps to container UID 0 in rootless containers. ([docs.podman.io][1])
    >   
    >   That produces this effective arrangement:
    >   
    >   ```text
    >   Host:
    >     socket owner = UID 1000
    >     socket mode  = typically 0660
    >   
    >   Inside rootless container:
    >     socket owner = UID 0
    >     builder/curl user = non-root UID
    >   ```
    >   
    >   The development container works because its process is probably UID 0. The curl image fails because its process is not UID 0. The Paketo lifecycle also runs as a non-root user, which explains the Maven failure: Spring Boot states explicitly that CNB images build as non-root users. ([Home][2])

    >   
    >   ## Why Maven reports `EOF` rather than permission denied
    >   
    >   The curl test fails before connecting:
    >   
    >   ```text
    >   Could not connect to server
    >   ```
    >   
    >   The lifecycle’s Go Docker client reports:
    >   
    >   ```text
    >   EOF
    >   ```
    >   
    >   Those are different client-level representations of the same underlying inability to communicate through the mounted socket. The lifecycle error is therefore not evidence of a malformed archive or invalid image identifier.
    >   
    >   ## SELinux mount options
    >   
    >   You currently use both:
    >   
    >   ```text
    >   --security-opt label=disable
    >   ```
    >   
    >   and:
    >   
    >   ```text
    >   :Z
    >   ```
    >   
    >   These are alternative approaches rather than complementary ones. Podman’s own documentation recommends mounting the socket and running the container with `--security-opt label=disable`. ([docs.podman.io][3])
    >   
    >   Use:
    >   
    >   ```bash
    >   --security-opt label=disable \
    >   --volume "${socket}:/run/podman/podman.sock:rw"
    >   ```
    >   
    >   without `:Z`.
    >   
    >   Relabelling a live user-service socket with `:Z` is unnecessary when container labelling is disabled and could interfere with other processes or containers using that socket.
    >   
    >   ## Diagnostic workaround
    >   
    >   Temporarily make the socket accessible to all container users:
    >   
    >   ```bash
    >   socket="${XDG_RUNTIME_DIR}/podman/podman.sock"
    >   
    >   chmod 666 "${socket}"
    >   ./mvnw spring-boot:build-image
    >   ```
    >   
    >   Then restore it:
    >   
    >   ```bash
    >   chmod 660 "${socket}"
    >   ```
    >   
    >   If the Maven build succeeds, that proves the non-root lifecycle user was blocked by the socket permissions.
    >   
    >   This is not a good general permanent configuration. Podman warns that access to its API socket gives effectively unrestricted control over the user’s Podman service and permits arbitrary code execution as that user. ([docs.podman.io][3])
    >   
    >   ## Practical permanent options
    >   
    >   The available solutions are constrained because Spring Boot creates the lifecycle container itself and does not expose general Podman options such as `--userns=keep-id`, `--user`, or supplemental groups.
    >   
    >   The practical choices are:
    >   
    >   1. **Use a controlled socket with broader permissions** on a dedicated development or CI account. This is straightforward but grants any process capable of opening the socket full Podman control.
    >   
    >   2. **Use a TCP Podman API endpoint protected by mutual TLS.** This avoids Unix UID mapping, but requires careful certificate configuration. Do not expose an unauthenticated Podman TCP endpoint.
    >   
    >   3. **Use `pack` or another CNB invocation where the container user namespace can be controlled**, rather than the Spring Boot plugin’s embedded lifecycle orchestration.
    >   
    >   4. **Use a custom wrapper or builder workflow** that performs the build in a container context where the lifecycle UID has access to the API socket.
    >   
    >   The Spring Boot configuration itself matches its documented Podman example exactly: a rootless Unix socket plus `bindHostToBuilder=true`. ([Home][2]) The failure appears to be a gap between that documented arrangement and rootless Podman’s ownership mapping when the CNB lifecycle runs as a non-root UID.
